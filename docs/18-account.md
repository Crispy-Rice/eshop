# 18 · 账号体系

账号、登录、封禁、注销。**第一期不接短信通道**（[01 §4](01-overview.md)、[16 §6](16-deployment.md)），
所以下面所有"没有验证码怎么办"的取舍都是从这一条推出来的。

表结构与约束见 [13 §用户](13-schema.md)，接口见 [15 §2.0 / §2.9](15-api-and-errors.md)。

---

## 1. 手机号为什么存三份

| 列 | 用途 | 可逆 |
|---|---|---|
| `phone_hash` | HMAC-SHA256，**查询与唯一约束**用 | 不可逆（但 11 位号码的字典空间小，见 §5 的说明） |
| `phone_cipher` | AES-256-GCM，客服查看用 | 可逆（要 `PHONE_ENC_KEY`） |
| `phone_masked` | `138****8888`，列表展示 | 不可逆 |

加密后没法 `WHERE phone = ?`，所以查询走的必须是哈希 —— 这也是**后台按手机号搜用户只能精确匹配**、
没法 LIKE 的原因（[15 §2.9](15-api-and-errors.md)）。

## 2. 状态与角色

```
status: 1 正常 ──封禁──> 2 封禁 ──解封──> 1 正常
   │
   └──注销（终态，不可逆）──> 3 注销
```

- **唯一写入口**是 `account/service.py` 的 `ban_user` / `unban_user` / `close_account` ——
  它们同时负责吊销令牌与写审计流水。别在别处直接改 `status`，否则登录拦截与审计会对不上。
- 状态迁移一律走 **CAS**（`repository.set_user_status_cas`，`WHERE status = :from`）。
  于是"重复封禁""封一个已注销的号""解封一个正常号"都会拿到 0 行并被转成明确报错，
  并发下也只有一个能成功。
- `role` 是 `buyer / merchant / admin / finance` 四档**写死的字符串**，没有角色-权限表。
  一期够用；真到"多个运营分管不同类目"时再引入 RBAC 与数据权限，那是重构不是加功能。

## 3. 封禁：为什么不是"立即生效"

**认证依赖不查库。** `core/deps.py` 的 `get_current_user` 只解 JWT、拿 `sub/role/shop_id`，
一次数据库都不碰 —— 这是每请求省一次查询的取舍。

后果：**封禁无法让已签发的 access token 立刻失效**。所以生效方式是：

1. 登录被拒（`ACCOUNT_BANNED`，`message` 里带运营填的理由）；
2. **吊销该用户全部 refresh token** → 他最多把当前这个 access token 用完，续不了期；
3. 已登录的会话在 **access token TTL（30 分钟）** 内仍可调业务接口。

★ 第 2 条有个容易写错的**顺序**问题：`account/service.py` 的 `refresh()` 必须**先判
账号状态、再判令牌是否已吊销**。反过来（也就是最初的写法）会得到一个自相矛盾的结果 ——
封禁既然吊销了全部 refresh token，那个"令牌已吊销"的分支就会先命中，于是被封的人拿到的
永远是「登录已过期，请重新登录」。他会照着做，然后再失败一次，**始终不知道自己的号已被
冻结、更不知道该找谁**。同一段代码的注释当初写的就是"被封禁的用户不该只看到一句模糊的
账号不可用"——意图是对的，顺序错了。

★ 这是**已知取舍，不是缺陷**。所以界面文案与接口文档都不能写"立即生效"。
若业务上必须即时（比如正在被刷单），杠杆是**调小 `jwt_access_ttl_minutes`**，
而不是给认证依赖加查询 —— 那会给全站每个请求都加一次库往返。

**粒度只有"禁止登录"**（不拦下单/评价/领券）。分粒度要另一套状态位与多点拦截，
第一版不值得；真要禁购/禁言，正确做法是给状态加位标志并在对应 service 入口检查。

**守卫**（都在 service 里，与 CAS 配合）：

- 不能封自己；
- 不能封平台账号（`admin` / `finance`）—— 一次误操作会把平台自己锁死，没有第二条救济路径；
- 已注销的账号不必封。

## 4. 口令生命周期

| 场景 | 接口 | 关键行为 |
|---|---|---|
| 用户自助改密 | `PUT /api/me/password` | 校验旧密码 → **吊销全部 refresh token** → **给当前会话补发一对新 token** |
| 用户忘了密码 | 运营在后台重置 | 生成随机临时口令（`core/security.py:generate_temp_password`）→ **只返回一次** → 吊销全部 refresh token |

- 改密为什么要"全吊销 + 给当前补发"：改密的动机常常就是"怀疑别人在用我的号"，
  留一条旧会话等于没改；给当前补发则用户自己无感，不用重新登录。
- 没有短信通道，**运营重置是唯一的兜底**。代价是运营会短暂地知道那个口令，所以：
  只显示一次、提示用户登录后立即自行修改、并在审计流水里留痕。
- **本期不做"强制下次登录改密"**：那要动登录响应 schema + 两端强制跳转，是另一块范围。

## 5. 注销：语义与 PII 清单

注销是**软删 + 匿名化**：账号行还在（订单、评价要能引用它），但"这个人"的痕迹被抹掉。

### 5.1 前置守卫（在**路由层**）

| 守卫 | 原因 |
|---|---|
| 名下有店铺 | 没有"停用店铺"机制；店主先要处理商品与在途订单 |
| 有未完成的订单（待付款/待发货/待收货/退款中） | 注销后没法收货、没法退款 |
| 有进行中的售后 | 同上，退款流程会断 |

★ 这三个守卫**必须放路由层**：要查 trade 与 aftersale，而 `account` 不能 import 下游模块的
service（[01 §2](01-overview.md) 的依赖方向，反向即环）。所以由下游暴露只读计数
（`trade.service.count_blocking_orders`、`aftersale.service.count_open_refunds`），
`account/router.py` 来编排。这与 `create_shop` 调 freight 是同一个套路。

★ **同一份守卫也供 `GET /api/me/deactivation` 预检**（`router._deactivation_blockers`）：
两处各写一遍必然漂，而漂的后果是"预检说能注销、提交却被拒" —— 那比没有预检更糟。

**为什么要预检**：原先只能在**提交之后**才告诉用户被挡，而那时密码已经输过了；
提示还只是一句转瞬即逝的 toast，既不说去哪处理、也没说有几笔。现在商城端点
「注销账号」先问这个接口，被挡就弹一个能点去处理的对话框（去订单 / 去退款售后 /
去商家后台），**根本走不到输密码那一步**。提交时若仍被挡（预检与提交之间状态会变：
刚下单、刚开店），前端重新查一次再按同一套话术说。

### 5.2 匿名化清单

| 位置 | 处理 |
|---|---|
| `account.user` | `phone_cipher` 覆写成无意义密文、`phone_masked` → 「已注销」、`password_hash` → 随机串（不可登录）、`nickname` → 「已注销用户」、`avatar`/`gender`/`birthday` 清空、`status=3`、`closed_at=now` |
| `account.user_address` | 全部软删（`status=2`），并覆写收货人姓名 / 电话 / 门牌三处强 PII |
| `account.refresh_token` | 全部吊销 |
| `trade.order_main` 收货人快照 | **保留不动** —— 法律与对账凭证（[07](07-order-and-split.md)） |
| `review.review` | **不动** —— 昵称是**实时读** `account.user` 的（不是快照列），改了 user 表的昵称，该用户全部历史评价立刻显示「已注销用户」 |
| 磁盘 `media/avatars/{user_id}/` | 提交后删除（IO 不进事务，用 `after_commit.defer`）；`reviews/`、`aftersale/` 的图**保留**（属交易记录） |

★ **`phone_hash` 刻意保留原值** —— 见 §5.3，它是冷静期机制的前提。
★ 匿名化与"删干净"之间的这条分界线（订单快照保留）是有意的：**法规要求留存交易记录**，
而我们要卸掉的是"这个人的联系方式"。

### 5.3 手机号：30 天冷静期 + 惰性释放

一条规则：**注销后 30 天内，同一个手机号不能再注册**（挡"注销 → 立刻重注册"刷新人券）。

实现机制值得单独说清，因为它决定了 `phone_hash` 为什么不能像其他列那样被覆写：

```sql
-- 手机号唯一性只对未注销的行生效
CREATE UNIQUE INDEX uk_user_phone_hash ON account."user" (phone_hash) WHERE status <> 3;
```

1. **注销时保留 `phone_hash`**：注册流程要靠它查出"这个号注销过、是否还在冷静期"。
   若覆写成与手机号无关的占位值，这条查询就永远查不到 —— 冷静期会**静默失效**。
2. **冷静期一过就能重新注册**：已注销的行**不在上面那个部分唯一索引里**，
   所以新行带着同样的 `phone_hash` 也能插进去 —— **不需要改写旧行**，
   省掉了一整套"腾位"操作与它的并发风险。这就是"惰性释放"：释放不是某个动作，
   而是索引的过滤条件本来就不覆盖已注销行。
3. **代价必须记住**：同号被重新注册后，同一个 `phone_hash` 下会**同时存在活跃行与已注销行**。
   所以**所有按手机号查用户的地方都必须显式区分**（`repository.get_live_user_by_phone_hash`
   / `get_closed_user_by_phone_hash`）；盲查会随机命中一行，登录会莫名报"账号已注销"。

### 5.4 注销后登录：与"手机号不存在"完全一致

注销账号再登录，回的是 `LOGIN_FAILED`（"账号或密码错误"），**与一个从未注册过的号完全一样**
（含 `_dummy_password_hash` 的时间抹平）。

这是刻意的：若回 `ACCOUNT_CLOSED`，任何人报一个手机号就能问出"这个号曾经注册过"——
**账号枚举**。注销后登不进来是本分 —— 号确实已经没了。

（`ACCOUNT_CLOSED` 这个错误码仍存在，用在**自助操作**上：拿着还有效的 access token 去改密/注销
一个已注销的账号时，如实告诉他。）

## 6. 留痕

`account.user_state_flow` 是不可变审计流水（仿 `trade.order_state_flow`）：
封禁 / 解封 / 注销 / 运营重置密码各留一行，记 `event`、状态前后值、`operator_type/id`、原因。

- `operator_type` 复用 `core.enums.OperatorType`：1 用户、4 平台。
- **应用角色只授 INSERT/SELECT**，由 `scripts/harden_grants.py` 的 `IMMUTABLE_TABLES` 收紧
  —— 从权限层面保证改不了。加审计表时**别忘了把表加进那个元组**。
- 流水与状态变更在**同一个事务**里：审计与状态必须同生共死。

## 7. 用户怎么联系平台

这条链路**原本不存在**。封禁提示写着「账号已被封禁，请联系客服」，而买家端
（`web-mall/src`）里**一处「联系 / 客服 / 热线 / 申诉」都搜不到** —— 页脚也早被删掉了。
后端那些「客服」全是**运营侧**概念（客服补发券、券码客服核销、`operator_type = 4 平台客服`、
`phone_cipher` 客服查看），没有一个买家够得着。所以那句话是个**死胡同**：让用户去
联系一个不存在的客服。

现在：联系方式由运营在后台「营销中心 → 站点设置」填，落在 `promotion.site_contact`
（**全站单行**，`CHECK (id = 1)`，三列 `NULL` = 未配置），经**公开**接口
`GET /api/site-contact` 下发。表结构见 [13 §1](13-schema.md)，接口见 [15 §2.10](15-api-and-errors.md)。

### 7.1 为什么是"静态联系方式"而不是工单

| 方案 | 结论 |
|---|---|
| **静态联系方式**（客服邮箱 / 电话 / 服务时间） | ✅ 采用。它**在未登录状态下就能用** —— 而被冻结的人本来就只能停在登录页 |
| 站内工单 / 申诉单 | ❌ 被封的人**登不进来**，看不到回复；而第一期没有短信 / 邮件通道能通知他。等于建了一个没人能读的收件箱。真要做，必须配套"留手机号 → 运营回电" |

这条理由推出一个硬约束：**这个接口必须公开**。把联系方式藏在「我的」里，
对被冻结的人等于不存在 —— 而那句"请联系客服"正是说给他们听的。

### 7.2 只展示在登录页与冻结提示

不铺到全站页脚（页脚此前已被有意去掉），也不放进「我的」：

- **登录页** —— 需要联系平台的人，往往正是登不进来的那批；
- **冻结提示** —— 同一块面板里就能看到"找谁"。

三项**都没配**时，界面只说事实（该账号已被冻结），**不写"请联系客服"** ——
不承诺一个不存在的渠道，正是这次要修掉的那个毛病。

### 7.3 措辞：「冻结」给买家，「封禁」给运营

买家看到的文案用「**冻结**」，运营后台与审计流水仍旧用「**封禁**」（那是动作术语）。
两个理由：一是「封禁」对着用户说偏重；二是 `account.user.status` 这一列**建表注释从
第一天写的就是「1正常 2冻结 3注销」**，是代码后来漂成了「封禁」——这里只是漂回去。

错误码本身仍是 `ACCOUNT_BANNED`：改的是措辞，不是状态语义。

### 7.4 提示是"面板"，不是 toast

冻结提示走登录卡片上的**持久面板**（标题 / 原因 / 联系方式分三行），不是 `ElMessage`
那种 3 秒就消失的 toast：封禁是用户**无法自行绕过**的终态拦截，提示必须留得住 ——
错过之后只剩"点了登录没反应"，连重读一遍都做不到。

原因也**不再拼进那句话里**。原来 `f"{base}：{reason}"` 拼出来的
「账号已被封禁，请联系客服：疑似刷单」，读起来像"客服的联系方式是疑似刷单" ——
冒号前面那句话把理由变成了它的宾语。现在理由走 `data.reason` 结构化下发，由前端排版。

★ **已登录**的人被封、令牌续不了期时，前端也不再提示「登录已过期，请重新登录」
（那是个永远不会成功的指引），而是走同一块面板 —— 见
`web-mall/src/api/http.ts` 里对刷新失败的判码。

## 8. 明确不做

| 不做 | 原因 |
|---|---|
| 短信验证码 / 第三方登录 | 前置是短信通道（资质 + 按条付费），这是第一期的现实约束 |
| 实名认证 | 只有真实交易或监管要求时才需要 |
| RBAC + 数据权限 | 现在只有四档写死的角色、单店演示，等真需要多人分管再动 |
| 风控（失败锁定之外的设备管理、异地提醒） | 没有真实流量时无法验证，做了也是摆设。已有的是登录失败计数 + 锁定（`MAX_FAILED_LOGINS` / `LOCK_MINUTES`） |
| 强制下次登录改密 | 见 §4，范围外 |
| 运营查看用户手机号明文 | 后台只回掩码，沿用 `/api/admin/users/lookup` 的既有口径 |
